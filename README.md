# cyber_office

Небольшая команда агентов Claude Code за пиксельными столами в своём виртуальном
офисе: ставишь задачу — агент берёт её в отдельный git-worktree, правит код,
результат приходит на ревью diff'ом, после одобрения сам вливается в `main`.
Можно раздавать не только отдельные задачи, но и целые «миссии» — агент-планировщик
сам разобьёт цель на подзадачи и раздаст команде. Есть Telegram-мост (задачи и
ревью из чата) и вкладка «Тесты» (прогон pytest других твоих репозиториев). Без
облаков и сторонних аккаунтов — только твоя подписка Claude Code и твой компьютер.

## Требования

- Python 3.11+ и git.
- Подписка Claude Code и CLI `claude` с выполненным входом в аккаунт (`claude` →
  `/login`). Без подписки можно всё равно посмотреть интерфейс целиком — см.
  «режим имитации» (`AO_FAKE=1`) ниже.

## Быстрый старт

```bash
git clone <URL-этого-репозитория> cyber_office
cd cyber_office
bash scripts/setup.sh
```

Скрипт проверит Python и git, создаст `.venv`, поставит зависимости, создаст `.env`
из примера, проверит `claude` (и подскажет, если не найден), подготовит `workspace/`
и учебный репозиторий `sandbox/`, затем запустит сервер и напечатает адрес — по
умолчанию `http://127.0.0.1:8600`. Скрипт идемпотентный, повторный запуск ничего не
ломает — им же потом просто перезапускать сервер.

**Windows (PowerShell):**

```powershell
git clone <URL-этого-репозитория> cyber_office
cd cyber_office
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1
```

При пустом `workspace/` (ни одной задачи ещё не было) главная страница сама
подскажет: «Поставь первую задачу в песочнице» — кнопка рядом открывает диалог
задачи с уже заполненным примером на `sandbox/calc.py`, ничего искать не надо.

### Установка и запуск вручную

Если не хочется через скрипт — те же шаги руками, они одинаковы на macOS, Linux
и Windows. Само окно .app (`app/desktop.py`, `scripts/build_app.sh`) — только для
macOS; на остальных ОС просто открывай интерфейс в браузере по адресу ниже.

**macOS / Linux:**

```bash
python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # при необходимости токены/настройки (AO_TG_TOKEN, AO_CLAUDE_BIN, …), см. разделы ниже
.venv/bin/python -m app.main            # http://127.0.0.1:8600
AO_FAKE=1 .venv/bin/python -m app.main  # имитация агентов — смотреть интерфейс без подписки
```

Открой `http://127.0.0.1:8600` в браузере.

Постоянно работающий сервер на Linux (без терминала) — пример systemd-юнита в
`scripts/cyber_office.service` (пути и `User=` внутри — подставить свои):

```bash
sudo cp scripts/cyber_office.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now cyber_office
```

**Windows (PowerShell):**

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python.exe -m app.main            # http://127.0.0.1:8600
$env:AO_FAKE=1; .\.venv\Scripts\python.exe -m app.main  # имитация агентов
```

Или запусти `scripts\run_windows.ps1` (либо `scripts\run_windows.bat`) из корня
проекта — они сами переходят в папку проекта и запускают `.venv\Scripts\python.exe`.
Claude Code CLI на Windows ставится как `claude.exe`/`claude.cmd` — если он не в
`PATH`, укажи путь явно через `AO_CLAUDE_BIN` (см. ниже). Затем открой
`http://127.0.0.1:8600` в браузере.

**Поиск `claude`:** переменная `AO_CLAUDE_BIN` (если задана) побеждает всё
остальное; иначе ищем `claude` в `PATH` (на Windows — `claude.cmd`/`claude.exe`);
если нигде не нашли — пробуем `~/.local/bin/claude`. Сервер отказывается стартовать
(кроме `AO_FAKE=1`) с понятной ошибкой, если ничего не нашлось.

## Интерфейс

Экран по умолчанию (`#view-planerka`, выбор вида запоминается в браузере под
`ao_view`) — «Планёрка»: сетка 2×2 из блоков-сводок над самой сценой офиса:

- **Ждёт тебя** — задачи в статусах «на ревью» и «ошибка», те же карточки и
  кнопки, что и на доске (одобрить/отклонить — если на ревью, повторить — если
  ошибка).
- **Сейчас в работе** — running-задачи: число ходов, сколько минут агент уже
  работает (по последней строке «агент начал работу» в логе задачи) и
  последняя реплика агента из ленты.
- **За сегодня** — сколько задач и миссий сделано с начала суток и расход по
  API (`GET /api/summary?since=YYYY-MM-DD`, см. REST ниже).
- **Последние события** — последние 10 строк общей ленты (агент/офис), без
  собственной прокрутки.

Под сводкой — свёрнутая сцена офиса (раскрывается кнопкой «показать офис»),
дальше лента агентов и доска задач (4 колонки: Очередь/В работе/На ревью/
Готово).

Слева, во всю высоту, — колонка **«Проекты»** (`#projects`): строка «Все
проекты» и каждый зарегистрированный репозиторий отдельно, со счётчиками
(сколько на ревью — жёлтая рамка, сколько в работе — синяя, сколько всего);
кнопка «＋» у заголовка открывает тот же диалог добавления репозитория, что и
«＋ репозиторий» в шапке. Клик по строке выставляет единый фильтр
(`REPO_FILTER`, хранится в `localStorage` под `ao_repo`) — он одновременно
перекраивает доску задач, все четыре блока Планёрки и (если выбран конкретный
репозиторий, а не «Все проекты») дерево вкладки «Тесты». На ширине ≤768px
список превращается в выпадающий `<select>` с теми же пунктами.

Колокольчик в шапке (`#btn-notify`) — независимый от общей ленты центр
уведомлений: копит события (миссия выполнена, задача перешла в
ревью/ошибку/готово, сбой API, результат хука `after_merge`) в `localStorage`
(`ao_notifications`, до 200 штук); бейдж на колокольчике — число непрочитанных
(до «99+»). Диалог со списком подсвечивает непрочитанные, кнопка «Прочитать
всё» гасит бейдж.

Карточка задачи (открывается кликом по любой карточке — на доске, в Планёрке
или в графе миссии) — четыре вкладки:

- **Резюме** — ответ агента мини-markdown'ом (`**жирный**`, `` `код` ``,
  списки, блоки кода) и, если задача упала, причина и таймер автоповтора.
- **Дифф** — слева дерево изменённых файлов (разбор unified diff по строкам
  `diff --git a/X b/Y`), клик по файлу прокручивает и подсвечивает блок
  справа. Работает не только для «на ревью»/«ошибка», но и для уже влитых
  (`done`) задач — см. REST ниже.
- **Лог** — короткая хроника задачи и полная лента событий
  (`GET /api/tasks/{id}/events`), слитые по времени в один список.
- **Промпт** — исходный текст, отправленный агенту.

Ниже вкладок — поле **«✍️ Дописать агенту»**, видимое для задач в статусах
running/failed/rejected. Для running-задачи оно шлёт
`POST /api/tasks/{id}/note` — текст сразу попадает в лог задачи и в очередь
уточнений (хранятся последние 20), которые агент увидит на следующем шаге;
поле остаётся открытым для новых дозаписей. Для failed/rejected то же поле
вместо note-ручки запускает «Повторить с уточнением»
(`POST /api/tasks/{id}/retry` с этим текстом) — отдельного вызова note для них
не нужно, у retry уже есть свой параметр с уточнением.

На карточке миссии под прогресс-баром — inline SVG-граф подзадач
(раскладка — чистая функция `ui/graph.js::computeGraphLayout`, юнит-тестируется
напрямую через `node`; разметка узлов, рёбер и обработка кликов — в
`ui/app.js::renderMissionGraph`). Слой узла — 0, если у задачи в наборе нет
зависимостей, иначе на единицу больше самого глубокого слоя среди её
`depends_on`; слои идут колонками слева направо, задачи одного слоя — друг под
другом. Обводка и заливка узла — цвет статуса (тот же, что и рамка карточки на
доске), внутри узла — аватар агента и название; клик по узлу открывает
карточку этой задачи.

Под названием узла — мелкая строка со временем: «⏱ 14 мин · 67 ходов» для
`done`/`review`/`failed` (длительность — от `started_at` до `finished_at`,
эти поля `Task` проставляет `office._run` при взятии задачи в работу и при
переходе в терминальный статус; для задач, созданных до появления этих полей,
длительность в `ui/app.js::taskDurationMinutes` считается по HH:MM:SS в
строках `log`), для `running` — растущий счётчик «⏱ 5 мин…» (перерисовывается
раз в 30с таймером, не через WS-событие), для `todo` — прочерк. Расход по API
на узле не показывается, он есть в сводке миссии.

Критический путь — самая долгая по времени цепочка зависимостей от корня до
листа — считает чистая функция `ui/graph.js::criticalPath(nodes, edges,
weights)` (юнит-тестируется через `node`, независимо от раскладки); вес узла —
фактическая длительность для `done`/`review`/`failed`, набегающая для
`running`, а для `todo` — медиана длительностей уже завершённых задач той же
миссии (15 минут, если оценивать не по чему). Узлы и рёбра критического пути в
`ui/app.js::renderMissionGraph` обводятся розовым неоном (`#ff4fa3`, то же
свечение, что у вывески в шапке), под графом подпись «Критический путь: 3
задачи · ~48 мин», а для активной миссии — ещё и «ожидаемое окончание ~14:20»
(сумма оставшихся оценок по узлам пути от текущего момента). При наведении на
узел — всплывающая подсказка (агент, статус, начало/конец, длительность,
ходы, ветка); на тач-устройствах (`hover: none`) первый тап только показывает
подсказку, второй — открывает карточку задачи, как обычный клик.

REST: `GET /api/tasks/{id}/diff` теперь отдаёт diff и для `done`-задач —
берётся не текущая ветка (её уже нет, worktree удалён после мерджа), а
сохранённый при одобрении `merge_commit`. `POST /api/tasks/{id}/note`
(`{"text": "..."}`) принимает дозапись только для задачи в статусе `running`,
для остальных статусов отвечает 400. `GET /api/summary?since=YYYY-MM-DD` —
сколько задач и миссий завершено с этой даты и суммарный расход по API; этим
запросом Планёрка наполняет блок «За сегодня».

## Оскар и кнопка «Что происходит?»

Кнопка «📋 Что происходит?» (`#btn-digest`) в шапке — быстрая сводка по всем
репозиториям без похода на доску: активные миссии с прогресс-баром
«сделано/всего», кто чем сейчас занят, задачи на ревью (клик открывает
карточку), упавшие за последние 24 часа с причиной, паузы репозиториев и
последний прогон test_hub (passed/failed, стенд), если он доступен. Поверх
этих фактов персонаж **Оскар · сводки и цифры** (сухой точный бухгалтер, сидит
за четвёртым столом, задач из очереди не берёт) пишет 3–5 предложений текста.

Кнопка загорается неоном не по расписанию, а только когда в фактах реально
что-то изменилось: раз в `AO_DIGEST_INTERVAL_MIN` минут планировщик
пересобирает факты и сравнивает их отпечаток с прошлым — если ничего не
изменилось, Оскара не дёргаем и кнопка остаётся обычной. Открыть модалку
можно в любой момент кликом по кнопке (`GET /api/digest` — из кэша, если он
есть), кнопка «↻ Обновить» в модалке форсирует пересбор независимо от
таймера и отпечатка (`POST /api/digest/refresh`). После закрытия модалки
свечение гаснет (`POST /api/digest/seen`).

Переменные окружения (см. также «Переменные окружения» ниже):

- `AO_DIGEST_INTERVAL_MIN` (по умолчанию `15`) — как часто, в минутах, планировщик
  пересобирает факты и проверяет, не появилось ли изменений.
- `AO_DIGEST_MODEL` (по умолчанию `haiku`) — модель, которой Оскар пишет текст
  поверх фактов (сами факты код считает без обращения к модели).

В Telegram та же сводка — командой `/digest`.

Стоимость минимальна: один вызов `claude -p` моделью `haiku` не чаще раза в
`AO_DIGEST_INTERVAL_MIN` минут, и то только если факты изменились с прошлой
сводки — в большинстве случаев вызовов ещё меньше.

## С телефона

По умолчанию сервер слушает только `127.0.0.1` — с телефона не достучаться. Чтобы
открыть интерфейс с телефона в той же Wi-Fi сети, что и ноутбук, разреши слушать
на всех интерфейсах:

```bash
AO_HOST=0.0.0.0 .venv/bin/python -m app.main
```

Узнай локальный IP ноутбука (`ipconfig getifaddr en0` на macOS) и открой в браузере
телефона `http://<IP-ноутбука>:8600` (Safari/Chrome, порт как у `AO_PORT`, по
умолчанию 8600).

На ширине экрана до 768px раскладка одноколоночная: `ui/style.css` переключается
на мобильный вид через `@media (max-width:768px)`, JS-логика переключений — в
`ui/app.js`, сам `ui/floor.js` не менялся (только реагирует на уже существующее
событие `resize` окна). Что работает:

- **Шапка** — вывеска, индикатор режима и колокольчик уведомлений остаются на
  виду, всё остальное (фон, темы, переключатель Планёрка/Офис/Тесты,
  репозиторий/задача/миссия) убрано в выпадающее меню по кнопке ☰.
- **Планёрка и «Проекты»** — сетка 2×2 сводок становится одной колонкой;
  список проектов слева сворачивается в выпадающий `<select>` над остальным
  содержимым (счётчики и «＋» пропадают, сам фильтр работает так же).
- **Сцена офиса** — свёрнута в полоску ~120px, кнопкой «показать офис»
  раскрывается на всю ширину с сохранением пропорций 768×432; лента агентов
  под ней — 40vh со своей прокруткой.
- **Доска задач** — вместо 4 колонок вкладки-чипы «Очередь/В работе/На
  ревью/Готово» со счётчиками, карточка на всю ширину, кнопки одобрить/
  отклонить/повторить — крупные, под палец; фильтр по репозиторию — тот же
  выпадающий список «Проекты», что и на Планёрке, отдельной ленты чипов у
  доски больше нет.
- **Карточка задачи** — вкладки Резюме/Дифф/Лог/Промпт идут одной
  прокручиваемой лентой; во вкладке «Дифф» дерево изменённых файлов — над
  самим диффом, а не колонкой слева.
- **Диалоги** (новая задача/миссия, свой prompt/confirm) — на весь экран,
  портрет в шапке уменьшен, поля крупные, кнопки отправки прилипают к низу и не
  перекрываются клавиатурой.
- **Тесты** — дерево тестов и лог прогона идут друг под другом; таблица отчёта
  Allure скроллится по горизонтали внутри себя, страница вбок не едет.

На десктопе (шире 768px) раскладка не меняется.

## Как это устроено

```
app/core/tasks.py     задачи в workspace/tasks.json: todo → running → review → done
app/core/worktree.py  ветка agent/<id> + git worktree на задачу; merge --no-ff после апрува
app/core/runner.py    ClaudeRunner: claude -p --output-format stream-json; FakeRunner для тестов
app/core/office.py    очередь по агентам (один агент — одна задача), ревью, reject/retry
app/core/planner.py   миссия -> план подзадач (claude в режиме только чтение, строгий JSON)
app/core/roster.py    состав офиса: workspace/roster.json (имя, роль, модель, стол)
app/core/memory.py    workspace/agents/<имя>/MEMORY.md — дописывается после каждой задачи
app/core/testlab.py   тесты чужого репо: discover()/run() через .venv репозитория, история в workspace/tests/<repo>/runs.json
app/core/scenarios.py Playwright-сценарии bike_fit: запись codegen'ом, запуск поверх testlab.run, скриншот падения
app/telegram.py       Telegram-мост: задачи из чата, карточки на ревью с кнопками
app/main.py           FastAPI: REST + WebSocket событий; ui/ — пиксельный офис (floor.js), лента, канбан, ревью
sandbox/              учебный git-репозиторий для экспериментов
```

Поводок: агент правит файлы только в своём worktree, из Bash ему разрешены
чтение, тесты и git-диагностика (`runner.ALLOWED_TOOLS`). В main попадает только
то, что ты одобрил на ревью, глядя на diff.

## Как устроен merge

При «Одобрить» офис не трогает рабочую копию пользователя. `Office.approve()`
вливает ветку агента не в основной чекаут репозитория (он может быть переключён
на чужую ветку или быть грязным), а в отдельном временном detached git worktree
(`workspace/worktrees/_merge_<hex>/`, живёт только на время мерджа и всегда
удаляется в `finally`, даже при ошибке). После успешного `git merge --no-ff` в
этом временном worktree база продвигается не через checkout, а через
`git update-ref refs/heads/<base> <sha>` прямо в основном репозитории —
рабочая копия пользователя при этом вообще не трогается.

Базовая ветка (`worktree.default_branch`) определяется так: явно заданное поле
`"base"` у репозитория в `workspace/repos.json` побеждает всё остальное — по
аналогии с уже описанным там полем `"after_merge"` (см. «Хук после мерджа» и
`workspace/repos.example.json`):

```json
{ "path": "~/projects/other-repo", "base": "develop" }
```

если поле не задано — ветка, на которую указывает `origin/HEAD` (без префикса
`origin/`), а если и её нет — первая существующая из `main`/`master`.

Настоящий конфликт мерджа (`CONFLICT` в выводе `git merge`) не роняет задачу
насовсем: merge в temp-worktree откатывается (`git merge --abort`), задача на
миг помечается «ошибка» и тут же автоматически уходит на повтор — агент
получает подсказку перенести готовую работу (`git cherry-pick`) поверх свежей
базы, кликать «Повторить» самому не нужно. Любая другая ошибка git (не
конфликт) — просто падает: задача остаётся в «ошибка» с полным текстом ошибки
git в логе, без автоповтора, разбираться нужно вручную.

Ветки `agent/<id>-prev`, которые `keep_previous()` заводит перед таким
автоповтором (хранят прошлую попытку — по ним агент делает `git diff`/
`cherry-pick`), теперь удаляются автоматически: как только следующий мердж
этой же задачи проходит успешно, `approve()` заодно чистит и `-prev`-ветку.

## Остановка и таймауты

На карточке running-задачи — кнопка **«⏹ Остановить»**: в интерфейсе (на
доске, в Планёрке и в карточке задачи) и такая же кнопка на карточке задачи в
Telegram-мосте. Обе дёргают `POST /api/tasks/{id}/stop` → `Office.stop()`
отменяет работающий `asyncio.Task` агента; отмена долетает до `_run()`/
`ClaudeRunner`, которые убивают процесс `claude` и всю его группу дочерних
процессов (`os.killpg(..., SIGKILL)`, процесс запускается в своей process
group именно для этого), задаче ставится причина «остановлена владельцем».
`DELETE /api/tasks/{id}` для running-задачи теперь тоже сначала сам
останавливает агента тем же путём и только потом чистит worktree и запись —
раньше висящий процесс приходилось убивать руками.

Таймауты по умолчанию — по истечении процесс так же убивается целиком вместе
с дочерними, без автоповтора, задача помечается «ошибка» с текстом таймаута:

| что таймаутится                                  | по умолчанию | переменная         |
|---------------------------------------------------|--------------|--------------------|
| запуск агента на задаче (`claude -p`)              | 90 мин (5400с) | `AO_TASK_TIMEOUT` |
| планирование миссии (Майкл, режим только чтение)   | 15 мин (900с)  | `AO_PLAN_TIMEOUT` |
| прогон тестов стороннего репозитория (вкладка «Тесты») | 30 мин (1800с) | — (константа `testlab.RUN_TIMEOUT`) |
| хук `after_merge`                                  | 2 мин (120с)   | — (константа в `Office.run_after_merge`) |

Настраиваются через `.env` только первые два; лимит на тесты и на
`after_merge`-хук зашиты в коде и через переменные окружения не меняются.

## Миссии

«🎯 Миссия» — одна большая цель. Майкл читает репозиторий (без правок) и отвечает
JSON-планом: 2–6 подзадач, исполнитель, зависимости. Подзадачи создаются как
обычные задачи; зависимая стартует, только когда её зависимости одобрены и влиты
в main — так она видит результат предыдущих. Конфликт при мердже офис устраняет
сам, без участия пользователя — см. «Как устроен merge».

## Новый проект из офиса

Чтобы миссия или задача под совсем новую идею не приземлилась по ошибке в чужой
репозиторий (или в `sandbox`), репозиторий можно создать прямо на месте — из
диалогов «Новая задача»/«Новая миссия», из отдельного диалога «Репозиторий»
или из Telegram.

**В диалогах задачи/миссии.** Первый пункт в селекте репозитория — «➕ Новый
проект…»; при выборе раскрываются поля: имя проекта (латиница/цифры/`_`/`-`),
шаблон (`python`/`web`/`empty`) и чекбокс «сделать .venv». При отправке сперва
создаётся проект (`POST /api/repos/new`), затем в нём — задача или миссия;
описание нового README берётся из цели миссии (или из описания задачи).
Репозитории в обоих селектах и колонке «Проекты» слева обновляются сразу же
(`loadState()`), без перезагрузки страницы.

**Кнопка «＋ репозиторий»** (и «＋» у заголовка колонки «Проекты») открывает
диалог с двумя вкладками: «Подключить существующий» (путь к готовому
git-репозиторию, как раньше) и «Создать новый» — те же поля, что и в диалогах
задачи/миссии.

**REST.** `POST /api/repos/new {"name", "description"?, "template"?, "venv"?}`
(`template` — `python`/`web`/`empty`, по умолчанию `empty`; `venv` — ставить ли
`.venv` для `python`, по умолчанию `true`) создаёт
`<AO_PROJECTS_DIR>/<name>`: `git init -b main`, `README.md` с названием и
описанием, `.gitignore` под шаблон, для `python` — пустой `requirements.txt` и
`tests/test_smoke.py`, первый коммит; репозиторий сразу регистрируется в
`workspace/repos.json`, как при обычном подключении. Для `python` с `venv:
true` `.venv` ставится в фоне (`python3 -m venv .venv`, не блокируя ответ) —
готовность (или причина неудачи) приходит событием `repo.ready`; о самом
создании репозитория интерфейс узнаёт по событию `repo.created` (строка в
ленте «📁 создан проект: …»). Плохое имя, занятое имя или неизвестный шаблон —
`400` с понятной причиной.

**Telegram.** `/newproject имя [описание]` (шаблон всегда `python`) и кнопка
«➕ Новый проект» в клавиатуре выбора репозитория (`/repo`, а также когда бот
спрашивает репозиторий для задачи без текущего) — после создания проект сразу
становится текущим для этого чата (`tg_prefs.json`), а если задача/миссия
дожидалась выбора репозитория — уходит в свежесозданный. Карточка «✉️
Принято»/«🎯 Миссия принята» всегда показывает целевой репозиторий и несёт
кнопку «🔁 сменить репозиторий».

**Защита от смешивания.** Если текст задачи/миссии содержит слова вроде «новый
проект», «сайт», «приложение», «бот», а выбранный репозиторий — не `sandbox` и
не «➕ Новый проект», под полем появляется жёлтая подсказка «Это точно в
`<repo>`? Может, новый проект?» (`ui/app.js::mixingWarning` — чистая функция,
юнит-тестируется через `node`, см. `tests/test_new_repo_ui.py`). Это только
подсказка, отправку она не блокирует.

## Пиксельный офис

`ui/floor.js` рисует мир 768×432 «пикселей» (раньше было 512×288) в offscreen-canvas
и масштабирует под размер контейнера. Спрайты — строки-сетки в коде: человечки
со своей причёской и цветом рубашки (цвет агента), стол со стулом и монитором.

**Сцена.** Контейнер `#floor` всегда вписывает мир 768×432 целиком, сохраняя пропорцию
16:9 (letterbox по одной оси, без обрезки и без искажений) — в CSS его высота считается
от ширины (`aspect-ratio:16/9`), с потолком `max-height:60vh` на десктопе; на мобильной
раскладке (≤768px) сцена, как и раньше, свёрнута в полоску ~120px и разворачивается по
кнопке, тоже во всю ширину и 16:9. Масштаб — чистая функция `fitScale(W, H, LW, LH)`
(`ui/floor.js`, экспортирована для node-тестов): `scale = min(W/LW, H/LH)`, не меньше
0.5 (совсем маленький контейнер не даёт нечитаемому масштабу утянуть сцену в пиксельную
кашу — сцена в этом случае может слегка не поместиться, канвас сам обрежет лишнее по
краям), а если дробное значение почти совпадает с целым (в пределах 0.08) — снапается к
целому, чтобы грани спрайтов оставались ровными без сглаживания. При отрисовке на экран
`ctx.imageSmoothingEnabled` включается только при `scale < 1` (чтобы не было «дырок»
между пикселями при уменьшении), при масштабе ≥1 остаётся выключенным для чёткости;
`canvas.width`/`height` учитывают `devicePixelRatio`. Пересчёт размеров идёт не только
по `window.resize`, но и через `ResizeObserver` на контейнере — это ловит и смену
вкладки Планёрка/Офис (`display:none` → видимый), и раскрытие мобильной полоски,
когда размеры контейнера меняются без события resize окна. Фото-фон (`setBackground`,
выпадающий список «Фон этажа») рисуется в тех же мировых координатах offscreen-канваса
по правилу cover (обрезка по короткой стороне, центрирование, без искажения пропорций
фото) — так он масштабируется вместе со сценой, а не отдельным CSS-слоем.

Сотрудники теперь всегда сидят за своим рабочим местом и никуда не ходят — ни к
лоткам «задачи»/«ревью», ни к кулеру или кофемашине, ни в центр комнаты. Рабочее
место (стол/секция стола с ретро-монитором в неоновой подсветке и креслом) —
часть самой cyberpunk-сцены, а не мебель, расставленная поверх неё; расстановкой
занимается `computeDeskPositions()` вместе с полосами `CYBER_DESK_BANDS` в
`ui/floor.js` — при 1–3 агентах места идут одним рядом, при 4–6 — двумя. Задача
или готовый документ прилетают агенту прямо на стол короткой анимацией падения
сверху, без похода к лоткам; подписи имени и текущего состояния над рабочим
местом остались как были.

Поза и анимация человечка меняются по тому же состоянию агента (`setState`),
что приходит из событийной шины, что и раньше:
- **idle** — сидит, дышит (лёгкое покачивание силуэта), изредка моргает и
  ненадолго поворачивает голову в сторону;
- **working** — печатает, монитор «бежит строчками» кода;
- **review** (ждёт ревью) — откинулся в кресле;
- **planning** — смотрит на светящийся график/голограмму у своего стола;
- **failed** — обхватил голову руками, монитор мигает красным вместо синего;
- **done** — победный жест, не вставая с места.

В офисе постоянно живут два кота (рыжий и серый) — гуляют по полу, обходя
препятствия сцены, иногда ложатся отдохнуть и мяукают в облачке-комиксе, а
иногда запрыгивают на столы — уже со стоящими на них компьютерами. Пока кот в
гостях у чьего-то стола, агент поворачивает голову в его сторону. Шрифт
Pixelify Sans (есть кириллица).

Для темы «Кибер» вместо старого рисованного этажа рисуется отдельная процедурная
ночная сцена: панорамное окно с силуэтами небоскрёбов и закатом, стеллаж, неоновая
колонна, декоративная мебель (кресла, длинный стол с ретро-мониторами, растение).
Для тем «Аркада» и «Game Boy» рисуется прежний рисованный этаж — перекрашенный под
палитру темы, в тех же координатах мира 768×432 и с той же рассадкой по местам
(`deskX`), что была до сидячих поз. Кто будет править сцену, найдёт в
`ui/floor.js`:
- `LW`/`LH` (`ui/floor.js:9`) — константы логического разрешения, от них считается
  вся геометрия;
- `sceneObstacleRects()` (`ui/floor.js:197`) — список прямоугольников-препятствий
  cyberpunk-сцены (стеллаж, колонна, кресла, декоративный стол, растение);
- `computeDeskPositions()` и `computeHomes()` (`ui/floor.js:230` и `:245`) —
  расстановка столов агентов по полосам с обходом препятствий;
- `isInsideObstacle()`/`pointOutsideObstacles()` (`ui/floor.js:207`) — проверка
  «точка ходьбы не внутри препятствия»; используется и для котов
  (`catRandomPoint`, `ui/floor.js:270`), и для похода кота к столу
  (`startCatDeskTrip`, `ui/floor.js:321`);
- `renderCyberStatic()` и `drawCyberBackground()` (`ui/floor.js:473` и `:563`) —
  статичные слои сцены кэшируются в offscreen-canvas `cyberStatic` и
  перерисовываются не чаще раза в секунду; поверх каждый кадр рисуются только
  дешёвые динамические эффекты — пульсация неона и вспышки окон в
  `drawCyberDynamicFX()` (`ui/floor.js:551`).

Селектор «Фон этажа» (`#bg`) в шапке — прежний прототип фото-фона (картинка вместо
пола/стены) для сравнения со сценой; по умолчанию выбрана рисованная сцена
(`Floor.setBackground`, `ui/floor.js:436`).

Три агента по умолчанию рисуются собственными cyberpunk-образами (силуэт, цвет кожи/глаз,
неоновые акценты — под портреты в `ui/assets/portraits/`), а не общим генератором людей:

| агент   | портрет (256×256)                  | образ на этаже                                         | roster color |
|---------|-------------------------------------|----------------------------------------------------------|--------------|
| michael | `ui/assets/portraits/beard.png`    | длинные волосы, борода, тёмно-синяя куртка, голубой неон | `#4f8cff`    |
| dwight  | `ui/assets/portraits/cyborg.png`   | лысый киборг, хром-имплант, led-полосы оранж/розовый     | `#ff9a3c`    |
| pam     | `ui/assets/portraits/pink.png`     | розовый ирокез, чёрная куртка, бирюзовый неон-воротник   | `#ff4fa3`    |

Маппинг имя → файл портрета: `app/core/roster.py::AVATAR_BY_NAME` (дефолт для
`workspace/roster.json` без поля `avatar`; в самом roster.json оно уже проставлено явно).
Отдаётся клиенту в `/api/state` вместе с агентом и рисуется кружком 24×32px в ленте
событий, на карточках задач и в шапке карточки миссии (`ui/app.js::avatarImg`).

Третий постоянный питомец — кибер-пёс (`dog`, `ui/floor.js`): чёрно-тёмно-синий силуэт с
бирюзовыми глазами и розовым огоньком на ошейнике; в теме «Кибер» по телу мигают неоновые
«схемы»-дорожки (`drawDogNeon`), в «Аркаде»/«Game Boy» — тот же спрайт без неона, монохромно.
Бегает быстрее котов, гуляет/садится/ложится у случайного стола, обходя ту же мебель
(`computeDogRoute` — BFS по грубой сетке с «string pulling»-спрямлением, не просто точка вне
препятствия, как у котов). Если кот оказывается ближе 60px — короткая погоня (не чаще раза в
2 минуты, `dogShouldChase`): кот убегает/прыгает на стол, а пёс садится под ним и «смотрит
вверх» 3–5с. На `task.review`/`task.done` (те же вызовы `Floor.envelope('out'/'banana', …)`, что
шлёт `app.js` — отдельная шина событий не понадобилась) подбегает к автору задачи и виляет
хвостом. Изредка лает в облачке-комиксе, как коты мяукают.

Спрайт тела для конкретного имени — `CHAR_PALETTE`/`CHAR_HAIRSTYLES`/`CHAR_HEADS` в
`ui/floor.js`: причёска (3 ряда), цвета кожи/волос/глаз и акценты поверх спрайта
(`drawCharAccents` — неон, имплант, led, наплечник). Незнакомые агентам имена
по-прежнему получают процедурного человечка (`HAIRSTYLES`/`FACE_ROWS`, цвет — `roster.color`).

**Чтобы добавить нового персонажа:** положить портрет в `ui/assets/portraits/`, добавить
запись в `AVATAR_BY_NAME` и цвет в `workspace/roster.json`, затем в `ui/floor.js` — палитру
в `CHAR_PALETTE`, 3 ряда причёски в `CHAR_HAIRSTYLES` (16 «пикселей» на ряд) и, по желанию,
акценты в `drawCharAccents`. Без этого шага агент просто получит процедурный силуэт.

Портреты в шапках диалогов (новая задача, миссия, свой `uiAsk`/`uiPrompt`/`uiConfirm`/`uiAlert`
вместо системных) и мини-аватар выбранного агента у селекта — живые (`ui/portrait_anim.js`):
моргают каждые 2.5–6с (иногда двойным морганием), «говорят» — рот чередует talk1/talk2/neutral
неровными интервалами 90–140мс ровно пока идёт печать реплики под именем персонажа (`.speech`
в шапке `dlg-new`/`dlg-mission`/`dlg-ask`). Реплика печатается посимвольно (`ui/speech.js::
typeMessage`, ~18мс/символ — общая функция для Пэм, Дуайта и Майкла, клик по реплике —
пропустить печать); у Дуайта/Майкла при открытии диалога это случайная фраза из 4–6 вариантов
(`ui/speech.js::DWIGHT_LINES`/`MICHAEL_LINES`), при выборе агента в «Новой задаче» реплика не
меняется — говорит всегда Дуайт. После успешной отправки — короткий ответ («Принял, отдаю в
работу.» / «Понял. Иду планировать.»), печатается быстрее (~10мс/символ) и держится 0.8с перед
закрытием диалога; при ошибке текст ошибки печатается в реплике так же, но красным
(`.speech.error`), и диалог остаётся открытым. При закрытии диалога незавершённая печать
останавливается (`typeMessage(...).cancel()`). Эмоции без новых кадров: `worried` (моргает
вдвое чаще, портрет темнее и чуть опущен) — у Пэм, когда текст диалога похож на ошибку
(`ошибк|error|failed|не удал`), и у Дуайта/Майкла при ошибке отправки; `happy` (лёгкое
покачивание, портрет ярче) — у Дуайта/Майкла после успеха. Кадр меняется сдвигом
`background-position` по спрайт-ленте `<name>_sheet.png` (1024×256, 4 кадра
neutral|blink|talk1|talk2), а не перерисовкой `<img>`. При `prefers-reduced-motion: reduce`
реплика появляется сразу целиком и остаётся только моргание — без речи и покачивания. Ленту
событий и карточки задач (`ui/app.js::avatarImg`) не анимируем — там портретов много, было бы
мельтешение.

## Темы оформления

Весь интерфейс — в пиксельном стиле (квадратные углы, ступенчатые тени, Pixelify
Sans, сетка на фоне). Три темы переключаются в шапке и запоминаются в браузере:
**Аркада** (неон, розовый/жёлтый), **Game Boy** (4 зелёных тона), **Кибер**
(тёмно-синий, голубой/розовый неон). Палитра пола офиса меняется вместе с темой
(`THEMES` в `ui/app.js`, `Floor.setTheme`); «Кибер» при этом меняет не только
палитру, но и саму сцену этажа — см. «Пиксельный офис».

## Telegram-мост

В `.env`: `AO_TG_TOKEN` (бот от BotFather) и `AO_TG_ADMINS` (tg_id через запятую —
только им бот отвечает; остальным показывает их id и молчит). Мост живёт внутри
процесса сервера и работает с тем же Office.

- любой текст → задача Майклу в текущий репозиторий; `@dwight текст` — другому агенту
- `/repo` — выбрать репозиторий, `/mission текст` — миссия, `/status` — доска, `/diff <id>`
- готовая задача приходит карточкой с кнопками **Одобрить / Отклонить / Diff**; отклонение
  спрашивает причину, она уходит агенту при «Повторить».

### Свой бот в Telegram

1. Напиши [@BotFather](https://t.me/BotFather) → `/newbot`, следуй подсказкам —
   получишь токен вида `123456:AA...`. Положи его в `.env` как `AO_TG_TOKEN`.
2. Узнай свой tg_id: перезапусти сервер и напиши что угодно своему боту — раз
   `AO_TG_ADMINS` ещё пуст, он ответит «Этот офис не твой. Твой id: `<число>`».
3. Впиши это число в `.env` как `AO_TG_ADMINS` (несколько — через запятую) и
   перезапусти сервер ещё раз. Теперь бот отвечает только тебе (и тем, кого
   добавил), остальным — только показывает их id и молчит.

## Хук после мерджа

В `workspace/repos.json` репозиторий можно задать объектом:
`{"path": "~/projects/my_bot", "after_merge": "./scripts/restart.sh"}`. После «Одобрить»
команда выполняется в каталоге репозитория (например, перезапуск бота на новом
коде), результат уходит в ленту и в Telegram.

## Тесты

Вкладка «Тесты» — прогон тестов стороннего репозитория (не cyber_office). Реестр —
`app/core/testlab.py`: обнаружение через `pytest --collect-only -q` и запуск через
`pytest -q` в `.venv` целевого репозитория, без git worktree — правки там не делаются.
История прогонов — `workspace/tests/<repo>/runs.json` (атомарная запись tmp+`.replace()`,
как у `app.core.tasks`; хранятся последние 200 прогонов на репозиторий).

REST: `GET /api/tests` (дерево тестов), `POST /api/tests/run` (запуск, сразу отдаёт
`run_id`, сам прогон — фоновая задача), `GET /api/tests/runs` (список прогонов),
`GET /api/tests/runs/{id}` (детали), `GET /api/tests/runs/{id}/events`. Вкладка живая:
вывод и статус стримятся через ту же WebSocket-шину (`/ws`), что и события агентов.

### Отчёт (Allure-style)

Если в `.venv` целевого репозитория стоит `allure-pytest`, `testlab.run()` сам
добавляет `--alluredir=workspace/tests/<repo>/allure-results/<run_id>` и помечает
прогон `allure=true`; если пакета нет — прогон идёт как раньше, без флага, а отчёт
собирается попроще из stdout (`app/core/allure.py`, поле `source: "allure"|"fallback"`
в ответе). У каждого прогона в истории — кнопка «Отчёт»: плашки passed/failed/broken/
skipped, кольцевая диаграмма и тренд по последним прогонам (обе — inline SVG, без
библиотек), таблица тестов с поиском/фильтром по статусу и раскрытием шагов/трейсбека/
вложений. REST: `GET /api/tests/report?repo=&run_id=`, `GET /api/tests/trend?repo=&limit=`,
`GET /api/tests/attachments/{run_id}/{source}`.

Кнопка «Открыть в Allure» на странице отчёта видна только если бэкенд нашёл сам Allure
CLI (`AO_ALLURE_BIN` в `.env`, иначе — `allure` в `PATH`; сам Allure сюда не ставим).
`GET /api/tests/allure-available?repo=&run_id=` решает, показывать ли кнопку;
`POST /api/tests/allure-open` (`repo`, `run_id`) прогоняет `allure generate … --clean`
по `allure-results` этого прогона и открывает получившийся `index.html` через `open`.

### Сценарии bike_fit

Для репозитория bike_fit есть отдельная вкладка «Сценарии» (`app/core/scenarios.py`):
Playwright-тест UI записывается через `playwright codegen` (кнопка «Записать» поднимает
локальный Streamlit bike_fit и открывает браузер записи; результат — pytest-файл в
`workspace/tests/bike_fit/scenarios`). Запуск сценария идёт через тот же `testlab.run` —
общая лента и история прогонов, просто с добавленными флагами
`--screenshot=only-on-failure --output=...`; при падении сохранённый скриншот отдаётся по
`GET /api/scenarios/screenshot/{run_id}/{filename}`. REST: `GET /api/scenarios` (список
файлов), `POST /api/scenarios/record`, `POST /api/scenarios/run`. Любой другой
репозиторий тестируется только обычным pytest — Playwright/UI-сценариев там нет,
эта вкладка завязана именно на bike_fit.

### Тесты сцены офиса

`tests/test_floor_js.py` гоняет чистые функции `ui/floor.js` напрямую через `node`
(модуль экспортирует их через `module.exports` — DOM/canvas не нужен) тем же
`pytest`, что и остальной проект; тесты пропускаются, если `node` не найден в
`PATH`. Проверяется: расстановка столов на cyberpunk-сцене не даёт им повиснуть
над препятствиями сцены или наехать друг на друга — для любого числа агентов от
1 до 6, с одним рядом и с двумя; именные персонажи (`CHAR_HEADS`/`CHAR_PALETTE`)
не путаются друг с другом и имеют корректный формат спрайта; сидячая поза не
пустая и реально различается между визуально разными состояниями (idle/working/
review/failed/done), а idle и planning намеренно используют одну и ту же ветку
выбора позы; в публичном API модуля больше нет функций хождения/поиска пути для
людей.

## Известные ограничения

- **Нет авторизации.** Кто угодно, кто может открыть `http://<адрес>:8600`, может
  ставить задачи, одобрять/отклонять чужие ревью и заливать код в `main` —
  никакого логина/пароля на входе нет и не планируется. Держи сервер на
  `127.0.0.1` (по умолчанию) или в доверенной сети (см. «С телефона»); за пределы
  доверенной сети/VPN не выставляй.
- Один сервер — один `workspace/` (второй экземпляр на тот же `workspace/` не
  стартует, см. `app.main.acquire_lock`), параллельно работать над одним офисом
  из нескольких мест нельзя.
- Агент читает/меняет только файлы своего git worktree, но команды из Bash ему
  разрешены (тесты, git-диагностика) — не подключай к офису репозитории, где
  чужой код в `.venv`/скриптах тестов не должен исполняться без присмотра.
